# Poncho v0.6.0 — Plan

> **Goal.** Two big themes: (1) **palette extensions** — bake richer per-cart palettes at convert time (curated master palette + cross-base blend ramps + optional wider sub-palettes); (2) **game-by-game validation** — prove the v0.3/v0.4/v0.5 stack works across the wider iNES library, with a regression harness that protects future work.

## Context

- v0.3 shipped a complete Poncho-NES runtime + a verbatim iNES → upscaled-mode `.poncho` converter. Contra plays at 99–100% pixel match against the reference NES emulator.
- v0.4 shipped AI-cache infrastructure + Phase 4.6 extended sub-palettes (84-shade ramps per base, computed at runtime from the 4 NES sub-palette colors). All ML model candidates were dropped from the UI; the Phase 5 work survives as runtime + format infrastructure.
- v0.5 shipped real-time pixel-art-aware scalers (xBRZ + MMPX) with palette-aware snap-back into the extended sub-palette + perceptual ramp interpolation.
- v0.6 picks up where v0.5 deliberately stopped: the runtime extended palette is generated from 4 sub-palette bases via interpolation, but the *stored* master palette is the canonical 64-entry NES palette. v0.6 widens both ends — a richer stored palette and a richer runtime layout — and validates the resulting stack against a wide library of converted games.

### Phase 1 — Curated per-cart master palette

**Goal.** Replace the canonical 64-entry NES master palette with a *curated* palette per converted cart. At convert time, scan the iNES PRG for the master indices the game actually writes to `paletteRam`, then **interleave interpolated neighbor colors** between those active indices. Net result: tiles get extra finely-graded master indices to land on without changing what the PRG sees.

**Why this works (where the v0.5 idea didn't).** The v0.5 conversation concluded that simply adding entries to the master palette is dead storage — the PRG only writes 0..63 indices into `paletteRam`. The leverage exists if we **rewrite the cart so PRG palette writes are intercepted and remapped**.

**Approach.**

1. **Static analysis pass** during `convertInesToPoncho`:
   - Scan PRG for `LDA #imm / STA $2007` patterns (palette writes during VBLANK) and any palette-table data (recognisable by 32-byte clusters of `0x00..0x3F`).
   - Build the set of master indices the game actually uses (typically 8-32 of the 64).
2. **Palette synthesis**:
   - For each used master index `m`, generate up to 3 interpolated neighbors: `(m, mid_1(m, m_neighbor), mid_2(m, m_neighbor), m_neighbor)`. Interpolation is in oklch (per v0.5 Phase 4 perceptual ramps).
   - Total stored entries grow from 64 to ~128-200 depending on the game's palette diversity. Format already supports `paletteCount` up to 65 535.
3. **PRG remapping** (the tricky part):
   - Patch the PRG so each `STA $2007`-during-VBLANK write that targets a known master index is rewritten to point at the *adjacent enriched index* in the new palette.
   - Because PRG can read arbitrary palette tables, we have to identify *all* palette-data sources, not just immediate-mode writes. Static analysis is fragile here; we'll accept "best-effort" with a fallback path: if the analyser can't safely rewrite, the cart ships with the original 64-entry palette and a flag `paletteCuration: false`.
4. **PpuUltra change**:
   - `paletteRam` widens to carry full 8-bit master indices (instead of the NES 0..63 range). Backward-compatible: existing carts have small index values, work unchanged.
   - The extended sub-palette generator now interpolates from 4 *richer-position* base colors per sub-palette → finer ramp gradients on the same shade count.

**Format change.**

- Add `flags.paletteCuration` (bit 3) to PonchoROM header.
- Bump format version (currently 1) → 2.
- v1 carts continue to load — flag clear, paletteRam constrained to 0..63.

**Quality bar.**

A cart ships with curation if **all** of:
1. The PRG remap pass terminates without ambiguity (no "we couldn't safely rewrite" warnings).
2. The curated cart renders pixel-identical to the original at frame N for `N ∈ {30, 60, 300}` (only the *master palette ABI* changed; rendered colors should be byte-identical to the v0.5 baseline because the curated entries replace the originals at the same RGB).
3. xBRZ output (Phase 5) snapped to the curated extended palette has measurably more distinct pv values than against the NES-canonical master.

If quality bar fails, the analyser flags the game as "uncurated" and the cart ships with format v1.

**Out of scope.** Tools to help users hand-curate ambiguous carts. Cross-cart palette sharing.

### Phase 2 — Wider sub-palette: 8 / 16 master indices per sub-palette

**Goal.** Lift the "4 base colors per sub-palette" cap from PpuUltra. Sub-palettes can store 8 or 16 master indices, drawn from the curated master palette in Phase 1. Lets PRG select richer base sets for tiles that are heavy on color variation.

**Why this matters.** The Phase 4.6 extended palette gives 84 shades per base, but only 3 bases (sub-palette entries 1, 2, 3 — entry 0 is universal-BG). A tile whose author wanted *four* distinct hues had to pick a different sub-palette. With 8-base sub-palettes, a single tile can express 7 hue centers + 84 ramp shades each = ~590 colors per sub-palette.

**Architectural shape.**

The NES PRG can't drive 8-base sub-palettes — it doesn't know they exist. So:

1. **Convert-time synthesis.** During `convertInesToPonchoAi`, group tiles by sub-palette, then *cluster the visually-similar source colors per sub-palette* and generate 4 additional master indices that sit between the 4 NES-shape bases.
2. **paletteRam widens.** PpuUltra's `paletteRam` becomes 64 bytes (8 sub-palettes × 8 indices) or 128 bytes (× 16) — config TBD per Phase 2 design.
3. **Tile pv encoding extends.** pv 0..255 currently encodes legacy + 3 ramps. With 8 bases the encoding becomes:
   - pv 0..7 — legacy slots (8 base colors verbatim)
   - pv 8..91 — ramp of base 1
   - pv 92..175 — ramp of base 2
   - …
   - With 8 ramps × 31 shades each ≈ 256 entries.
4. **Sprite-vs-BG split.** Sprites stay on NES-shape 4-base sub-palettes (no sprite-extended-palette work in this phase — see Phase 3).

**Format change.**

- New header field `subPaletteWidth` (uint8: 4, 8, or 16). Default 4 = NES-shape backward-compat.
- Bump format version → 3.

**Quality bar.**

- Phase 1 + Phase 2 stacked: a curated 8-base cart shows visibly more color depth than v0.5's 4-base cart on the smoke set.
- Backward compatibility: a `subPaletteWidth: 4` cart converted under v0.5 still loads identically under v0.6.

**Out of scope.** Backwards-rewriting PRG to take advantage of wider sub-palettes (PRG sticks to NES-shape `$2007` writes; the convert pipeline does the synthesis).

### Phase 3 — Cross-base blend ramps + sprite extended palette

**Goal.** Two carry-over items from the v0.5 "deferred" list, batched here because they touch the same code path (`buildExtendedSubPalette` + sprite render).

**3a. Cross-base blend ramps.** xBRZ (and any future scaler) producing a midpoint between pv values from *different bases* currently has nowhere clean to land. Solution: carve a small "cross-blend" zone at the top of the pv encoding (e.g. pv 240..255) representing common cross-base midpoints — 1↔2, 2↔3, 1↔3, 0↔1, 0↔2, 0↔3. ~16 slots, 4 perceptual shades per cross-blend.

**3b. Sprite extended palette.** Phase 4.6 only extended BG. Sprite render path stays NES-shape today. Lifting it requires:
- Sprite render's pv decoding extended to handle pv 4..255 same way BG does.
- Sprite-0 hit semantics need careful handling — the hit-detect fires when sprite pv 1..3 overlaps BG pv 1..3. With extended palette the "is this a non-zero pixel" predicate widens, but the hit semantics should stay anchored to legacy pv 0..3 to preserve game compatibility.
- 8×16 sprite mode + sprite priority semantics carry over unchanged.

**Tests.**

- Cross-blend: synthesise a tile with known cross-base pv values, verify rendered RGB matches the expected oklch midpoint.
- Sprite extended: regression test against existing sprite-heavy carts (Battletoads, Castlevania II) — pixel-identical rendering when sprite tiles use only legacy pv 0..3.

### Phase 4 — Game-by-game validation

Boot each title through the converter, observe what works, fix what breaks. Each game gets a frame-N screenshot baseline + a targeted issue list. Order is roughly easiest-first:

| Game | Mapper | Notable features needed |
|---|---|---|
| **Donkey Kong** | NROM | basic CHR-ROM render |
| **Super Mario Bros.** | NROM | scrolling + sprite-0 hit (status bar) |
| **Castlevania** | UxROM | sibling of Contra — likely works out of the box |
| **Mega Man 2** | MMC1 | CHR-RAM, mirroring control, PRG mode swap |
| **Battletoads** | AxROM | single-screen mirror toggle, heavy sprite usage |
| **Super Mario Bros. 3** | MMC3 | scanline IRQ counter accuracy stress |
| **Final Fantasy / Zelda** | MMC1 | battery-backed save (deferred unless trivial) |

Bug fixes that surface during validation are backported as point releases (`0.6.x`). The runtime is feature-complete; this is purely about polishing rough edges against real software.

**Effort.** ~5–10 days, with some games potentially exposing runtime quirks that loop back to a small PpuUltra/PonchoMapper fix.

### Phase 5 — Headless regression harness

`npm run test:games` — CI-friendly per-game runner:

1. Reads `tests/conversion/games.json` (per-game: input path, baseline screenshot, frame-N to capture, optional input scripts to advance past title)
2. Converts iNES → `.poncho` in memory
3. Runs N frames in PonchoNes (with optional scripted input)
4. PNG-diffs against baseline
5. Optionally captures audio buffer for diff

Output: per-game pass/fail with diff-region coordinates if mismatched. Locks in known-good state.

## Deferred (not in v0.6)

These items appear in the broader roadmap (`ROADMAP.md`) but aren't v0.6 work:

- Save states / battery SRAM persistence (touches many mappers)
- MMC2 / MMC5 / VRC6 / Color Dreams family mappers
- DMC DMA CPU stall (per [`DEFERRED.md`](../DEFERRED.md))
- Sub-cycle bus alignment for blargg-perfect timing
- Native-mode authoring tools (handcrafted Poncho games)
