# Poncho v0.6.0 — Plan

> **Goal.** Two big themes: (1) **palette extensions** — bake richer per-cart palettes at convert time (curated master palette + cross-base blend ramps + optional wider sub-palettes); (2) **game-by-game validation** — prove the v0.3/v0.4/v0.5 stack works across the wider iNES library, with a regression harness that protects future work.

## Context

- v0.3 shipped a complete Poncho-NES runtime + a verbatim iNES → upscaled-mode `.poncho` converter. Contra plays at 99–100% pixel match against the reference NES emulator.
- v0.4 shipped AI-cache infrastructure + Phase 4.6 extended sub-palettes (84-shade ramps per base, computed at runtime from the 4 NES sub-palette colors). All ML model candidates were dropped from the UI; the Phase 5 work survives as runtime + format infrastructure.
- v0.5 shipped real-time pixel-art-aware scalers (xBRZ + MMPX) with palette-aware snap-back into the extended sub-palette + perceptual ramp interpolation.
- v0.6 picks up where v0.5 deliberately stopped: the runtime extended palette is generated from 4 sub-palette bases via interpolation, but the *stored* master palette is the canonical 64-entry NES palette. v0.6 widens both ends — a richer stored palette and a richer runtime layout — and validates the resulting stack against a wide library of converted games.

## Phases

### Phase 1 — Per-cart palette enrichment

**Goal.** At convert time, scan the game's actual sub-palette usage, synthesize Oklab-interpolated intermediate colors between the NES master indices the game uses, store them in the `.poncho` master palette, and wire both the bake path and the runtime path to use the cart's enriched palette. Players see measurably smoother color gradients on shaded surfaces in the xBRZ-baked output.

**Why this is needed — two problems found in v0.5.**

1. **Bake/runtime palette mismatch (bug).** `XbrzUpscaleClient.upscaleTile()` calls `packedMasterPalette()`, which always returns the hardcoded canonical 64-color NES table. At runtime, `PpuUltra` instead calls `setMasterPalette(cart.palette)` — the palette stored in the `.poncho`. Because they differ, the same pv value resolves to a different RGB at bake time vs. runtime. Cached tiles are subtly wrong.

2. **Every converted cart stores the same 64-color NES palette.** `convertInesToPoncho` writes `NES_MASTER_PALETTE_RGBA` verbatim into every `.poncho` it produces. No per-game enrichment happens. The extended sub-palette ramps (`buildExtendedSubPalette`) interpolate between those 4 raw NES RGB positions. Adding intermediate colors between the game's actual used colors gives xBRZ snap-back more accurate shades to land on, and gives the Oklab ramps better-positioned endpoints.

**How the PRG-write problem is solved without PRG patching.**

The original Phase 1 plan called for patching PRG bytecode so `STA $2007` writes are rewritten to point at enriched palette indices. Code-level static analysis is fragile and hard to verify. A simpler, equivalent mechanism exists: a **64-byte runtime remap table** stored in the `.poncho`. When PpuUltra processes a `$3F00–$3F1F` VRAM write (palette RAM), it substitutes `paletteRemap[value]` before storing. The PRG bytecode is untouched; the remap lives in the cart data. One line in `PpuUltra.vramWrite`:

```ts
// line 974 currently:
this.paletteRam[mirrorPaletteAddr(addr)] = value;

// with remap (one lookup, null-safe):
this.paletteRam[mirrorPaletteAddr(addr)] = this.paletteRemap?.[value] ?? value;
```

**Approach.**

1. **Palette scan** in `convertInesToPoncho`:
   - Scan PRG for recognisable 32-byte palette-table clusters (bytes all in `0x00..0x3F`) — these are the VBLANK upload buffers. No instruction-pattern analysis needed; data-pattern scanning is reliable and game-agnostic.
   - Collect the set of NES master indices the game actually uses (typically 8–24 of the 64).

2. **Palette synthesis**:
   - Sort the used indices by Oklab perceptual distance from black.
   - For each adjacent pair `(a, b)` in that order, synthesize 1–3 intermediate entries at Oklab midpoints. Interpolation uses the same `oklchToSrgb` / `srgbToOklch` helpers from `src/runtime/oklch.ts`.
   - Append the synthesized entries to the master palette (indices 64+). The format already supports `paletteCount` up to 65 535 via the uint16 field in the header.
   - Build a 64-byte remap table: for each original NES index `i`, `remap[i]` points to the enriched entry at 64+ that best replaces it (the synthesized variant anchored at `i`'s Oklab position). Indices the game never uses self-map (`remap[i] = i`).

3. **Store in `.poncho`**:
   - Write the enriched master palette (64 canonical + N synthesized entries) as the cart's palette section. Existing `writePoncho` already accepts variable-length palette.
   - Store the 64-byte remap table as a new optional field in the PonchoROM header (or as a compact fixed trailer to the palette section — TBD during implementation).
   - Bump format version 1 → 2. v1 carts load identically — `paletteRemap` is null, remap is skipped.

4. **Fix `XbrzUpscaleClient`**:
   - Remove `packedMasterPalette()` (the hardcoded canonical table).
   - `XbrzUpscaleClient` constructor accepts `masterPalette: Uint32Array` (already packed ABGR). Both convert-time caller (`convertInesToPoncho`) and runtime caller (`UpscaleWorker`) pass the cart's actual palette.
   - The `upscale-registry.ts` `create()` factory signature gains an optional `masterPalette` parameter; `XbrzUpscaleClient` falls back to canonical NES if omitted (safe for tests that don't supply a cart).

5. **PpuUltra + PonchoCartridge**:
   - `PonchoCartridge` exposes `readonly paletteRemap: Uint8Array | null` (64 bytes or null).
   - `PonchoNes` passes it to PpuUltra via a new `setPaletteRemap(table: Uint8Array | null)` setter.
   - `PpuUltra.vramWrite` applies the remap before storing into `paletteRam`. `extendedPalettesValid` is invalidated on remap change (same path as master palette change).

**Format change.**

- Master palette section grows from 64 entries to 64 + N (N synthesized entries). `paletteCount` in header updated. Already a uint16; no overflow risk.
- New optional 64-byte remap block. Location TBD (trailing the palette section is simplest; a header flag bit indicates presence). Format version 1 → 2.
- v1 carts: `paletteRemap = null`, PpuUltra skips the remap, identical behavior to v0.5.

**Deliverables.**

1. `src/convert/palette-scan.ts` — `scanUsedPaletteIndices(prg: Uint8Array): Set<number>`. Identifies 32-byte palette-data clusters in PRG.
2. `src/convert/palette-enrich.ts` — `enrichPalette(usedIndices, nesRgba): { palette: Uint8Array, remap: Uint8Array }`. Synthesizes intermediate entries and remap table.
3. `convertInesToPoncho` updated — calls scan + enrich, writes enriched palette and remap into the `.poncho`.
4. `PonchoCartridge` — exposes `paletteRemap`.
5. `PpuUltra` — `setPaletteRemap` + one-line remap in `vramWrite`.
6. `XbrzUpscaleClient` — accepts cart palette; `packedMasterPalette()` removed.

**Tests** in `tests/convert/palette-enrich.test.ts` and `tests/runtime/ppu-ultra-remap.test.ts`:

- `scanUsedPaletteIndices` finds the correct index set for a synthetic PRG with a known palette table.
- `enrichPalette` produces `palette.length > 64 * 4` and `remap[i] >= 64` for every used index.
- All `remap[i]` values are valid indices into the enriched palette.
- `remap[i] == i` for indices the game never uses (self-map → no behavior change on those writes).
- PpuUltra: after a simulated `$3F01` write of NES index `0x16` with a remap table, `paletteRam[1]` holds the remapped value, not `0x16`.
- `XbrzUpscaleClient`: constructed with a synthetic 2-entry master palette; verify `upscaleTile` produces pv values in range 0..255 based on that palette (not the canonical 64-entry one).
- Round-trip: `convertInesToPoncho` on a known `.nes` → load as `PonchoCartridge` → `cart.paletteRemap` is non-null and length 64.
- Backward compat: a v1 `.poncho` (no remap block) loads with `paletteRemap === null`; PpuUltra produces byte-identical output to v0.5.

**Acceptance.**

- A game with known palette usage (Contra is the regression baseline) converts to a v2 `.poncho` with an enriched palette.
- PpuUltra runtime: a `$3F01` write of the NES red index is transparently remapped to the enriched red entry; extended sub-palette is rebuilt from the richer base.
- xBRZ-baked `.poncho` shows more distinct pv values on shaded surfaces than the v0.5 baseline.
- v1 carts unchanged: `remap = null` path in PpuUltra is byte-identical to v0.5 output.
- All Phase 1 tests + full test suite green.

**Out of scope.** PRG bytecode patching. Tools to hand-curate ambiguous carts. Cross-base blend ramps (Phase 3). Wider sub-palettes (Phase 2).

### Phase 2 — Wider sub-palette: 8 / 16 master indices per sub-palette

**Goal.** Lift the "4 base colors per sub-palette" cap from PpuUltra. Sub-palettes can store 8 or 16 master indices, drawn from the curated master palette in Phase 1. Lets PRG select richer base sets for tiles that are heavy on color variation.

**Why this matters.** The Phase 4.6 extended palette gives 84 shades per base, but only 3 bases (sub-palette entries 1, 2, 3 — entry 0 is universal-BG). A tile whose author wanted *four* distinct hues had to pick a different sub-palette. With 8-base sub-palettes, a single tile can express 7 hue centers + 84 ramp shades each = ~590 colors per sub-palette.

**Architectural shape.**

The NES PRG can't drive 8-base sub-palettes — it doesn't know they exist. So:

1. **Convert-time synthesis.** During `convertInesToPonchoAi`, group tiles by sub-palette, then *cluster the visually-similar source colors per sub-palette* and generate 4 additional master indices that sit between the 4 NES-shape bases.
2. **paletteRam widens.** PpuUltra's `paletteRam` becomes 64 bytes (8 sub-palettes × 8 indices) or 128 bytes (× 16) — config TBD per Phase 2 design.
3. **Tile pv encoding extends.** pv 0..255 currently encodes legacy + 3 ramps. With 8 bases the encoding becomes:
   - pv 0..7 — legacy slots (8 base colors verbatim)
   - pv 8..91 — ramp of base 1
   - pv 92..175 — ramp of base 2
   - …
   - With 8 ramps × 31 shades each ≈ 256 entries.
4. **Sprite-vs-BG split.** Sprites stay on NES-shape 4-base sub-palettes (no sprite-extended-palette work in this phase — see Phase 3).

**Format change.**

- New header field `subPaletteWidth` (uint8: 4, 8, or 16). Default 4 = NES-shape backward-compat.
- Bump format version → 3.

**Quality bar.**

- Phase 1 + Phase 2 stacked: a curated 8-base cart shows visibly more color depth than v0.5's 4-base cart on the smoke set.
- Backward compatibility: a `subPaletteWidth: 4` cart converted under v0.5 still loads identically under v0.6.

**Out of scope.** Backwards-rewriting PRG to take advantage of wider sub-palettes (PRG sticks to NES-shape `$2007` writes; the convert pipeline does the synthesis).

### Phase 3 — Cross-base blend ramps + sprite extended palette

**Goal.** Two carry-over items from the v0.5 "deferred" list, batched here because they touch the same code path (`buildExtendedSubPalette` + sprite render).

**3a. Cross-base blend ramps.** xBRZ (and any future scaler) producing a midpoint between pv values from *different bases* currently has nowhere clean to land. Solution: carve a small "cross-blend" zone at the top of the pv encoding (e.g. pv 240..255) representing common cross-base midpoints — 1↔2, 2↔3, 1↔3, 0↔1, 0↔2, 0↔3. ~16 slots, 4 perceptual shades per cross-blend.

**3b. Sprite extended palette.** Phase 4.6 only extended BG. Sprite render path stays NES-shape today. Lifting it requires:
- Sprite render's pv decoding extended to handle pv 4..255 same way BG does.
- Sprite-0 hit semantics need careful handling — the hit-detect fires when sprite pv 1..3 overlaps BG pv 1..3. With extended palette the "is this a non-zero pixel" predicate widens, but the hit semantics should stay anchored to legacy pv 0..3 to preserve game compatibility.
- 8×16 sprite mode + sprite priority semantics carry over unchanged.

**Tests.**

- Cross-blend: synthesise a tile with known cross-base pv values, verify rendered RGB matches the expected oklch midpoint.
- Sprite extended: regression test against existing sprite-heavy carts (Battletoads, Castlevania II) — pixel-identical rendering when sprite tiles use only legacy pv 0..3.

### Phase 4 — Game-by-game validation

Boot each title through the converter, observe what works, fix what breaks. Each game gets a frame-N screenshot baseline + a targeted issue list. Order is roughly easiest-first:

| Game | Mapper | Notable features needed |
|---|---|---|
| **Donkey Kong** | NROM | basic CHR-ROM render |
| **Super Mario Bros.** | NROM | scrolling + sprite-0 hit (status bar) |
| **Castlevania** | UxROM | sibling of Contra — likely works out of the box |
| **Mega Man 2** | MMC1 | CHR-RAM, mirroring control, PRG mode swap |
| **Battletoads** | AxROM | single-screen mirror toggle, heavy sprite usage |
| **Super Mario Bros. 3** | MMC3 | scanline IRQ counter accuracy stress |
| **Final Fantasy / Zelda** | MMC1 | battery-backed save (deferred unless trivial) |

Bug fixes that surface during validation are backported as point releases (`0.6.x`). The runtime is feature-complete; this is purely about polishing rough edges against real software.

**Effort.** ~5–10 days, with some games potentially exposing runtime quirks that loop back to a small PpuUltra/PonchoMapper fix.

### Phase 5 — Headless regression harness

`npm run test:games` — CI-friendly per-game runner:

1. Reads `tests/conversion/games.json` (per-game: input path, baseline screenshot, frame-N to capture, optional input scripts to advance past title)
2. Converts iNES → `.poncho` in memory
3. Runs N frames in PonchoNes (with optional scripted input)
4. PNG-diffs against baseline
5. Optionally captures audio buffer for diff

Output: per-game pass/fail with diff-region coordinates if mismatched. Locks in known-good state.

- Save states / battery SRAM persistence (touches many mappers)
- MMC2 / MMC5 / VRC6 / Color Dreams family mappers
- DMC DMA CPU stall (per [`DEFERRED.md`](../DEFERRED.md))
- Sub-cycle bus alignment for blargg-perfect timing
- Native-mode authoring tools (handcrafted Poncho games)
