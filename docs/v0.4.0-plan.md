# Poncho v0.4.0 — Plan

> **Goal.** Validate the v0.3 runtime + converter against a wide library of converted iNES games, build a regression harness so each game's pixel output is locked in, and lay the groundwork for AI-driven CHR upscaling.

## Where v0.3 left off

- v0.3 shipped a complete Poncho-NES runtime (PpuUltra modes, PonchoMapper variants for NROM/MMC1/UxROM/CNROM/MMC3/AxROM, per-scanline rendering, sprite-0 hit, 8×16 sprites).
- The iNES → upscaled-mode `.poncho` converter handles all 6 banking variants and plays Contra at 99-100% pixel match outside heavy-sprite scenes.
- See [`v0.3.0-plan.md`](v0.3.0-plan.md) for the full runtime story.

v0.4 is **all converter / validation track** — no major runtime changes are planned. Bug fixes that surface during game-by-game validation will be backported as point releases.

## Phases

### Phase 1 — Game coverage (lead validation games)

Boot each game through the converter, observe what works, fix what breaks. Order is roughly easiest-first within each mapper family:

| Game | Mapper | Notable features needed |
|---|---|---|
| **Donkey Kong** | NROM | basic CHR-ROM render — should be trivial |
| **Super Mario Bros.** | NROM | scrolling + sprite-0 hit (status bar) |
| **Mega Man 2** | MMC1 | CHR-RAM, mirroring control, PRG mode swap |
| **Castlevania** | UxROM | (sibling of Contra — likely works out of the box) |
| **Battletoads** | AxROM | single-screen mirror toggle + heavy sprite usage |
| **Super Mario Bros. 3** | MMC3 | scanline IRQ counter accuracy |
| **Final Fantasy / Zelda** | MMC1 | battery-backed save (deferred unless trivial) |

Each game gets a frame-N screenshot baseline + targeted issue list. Ship games as they pass.

**Effort.** ~5-10 days, with each game potentially exposing a runtime bug that loops back to a small PpuUltra/PonchoMapper fix.

### Phase 2 — Headless regression harness

`npm run test:games`: a CI-friendly runner that, for each curated game:

1. Reads `tests/conversion/games.json` (per-game: input path, baseline screenshot, frame-N to capture, optional input scripts to advance past title)
2. Converts iNES → `.poncho` in memory
3. Runs N frames in PonchoNes (with optional scripted input)
4. PNG-diffs against baseline
5. Optionally captures audio buffer for diff

Output: per-game pass/fail with diff-region coordinates if mismatched. Locks in known-good state so future runtime changes don't regress.

**Effort.** ~2-3 days.

### Phase 3 — AI upscaling option (post-MVP)

Optional pre-pass in the converter: replace the runtime's 4×4 nearest-neighbour CHR upscaling with an AI model's output. The runtime stays unchanged because the upscaled CHR is still 32×32 8 bpp tiles; the format flag flips from `upscaledMode=1` (PpuUltra does the upscale at render) to `upscaledMode=0` (CHR pre-upscaled, no runtime upscale).

Use cases:
- **Static CHR-ROM games** (Donkey Kong, SMB) — pre-bake all CHR tiles via AI upscale
- **CHR-RAM games** (Contra) — emulate the game offline, capture each unique CHR-RAM state, AI-upscale each, expose them as Poncho-CHR banks indexed by a state-hash table built into the mapper

The format already supports both endpoints; this phase just adds the pre-pass.

**Effort.** Variable — depends on model choice + pipeline. Likely 1-2 weeks for a working prototype.

### Phase 4 — Polish + release packaging

- Update `docs/consoles.md` with the verified game list
- Update `README.md` with screenshots from at least 3 working games
- Verify the web shell + Convert button work end-to-end with each curated game
- Tag v0.4.0

**Effort.** ~2-3 days.

## Deferred (not in v0.4)

These items appear in the broader roadmap (`ROADMAP.md`) but aren't v0.4 work:

- Save states / battery SRAM persistence (would touch many mappers)
- MMC2 / MMC5 / VRC6 / Color Dreams family mappers
- DMC DMA CPU stall (per [`DEFERRED.md`](../DEFERRED.md))
- Sub-cycle bus alignment for blargg-perfect timing
- Native-mode authoring tools (handcrafted Poncho games)

## Total estimate

~3–4 weeks calendar time, primarily gated on Phase 1's per-game debugging cycles.
