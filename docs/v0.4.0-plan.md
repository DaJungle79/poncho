# Poncho v0.4.0 — Plan

> **Goal.** Replace the runtime's 4×4 nearest-neighbour CHR upscaling with AI-generated 32×32 8 bpp tiles produced by **client-side upscale models** (e.g. ESRGAN-tiny / ONNX on WebGPU). Two workflows, one per cart type:
>
> - **CHR-ROM games** — bake all tiles at conversion time with a progress bar. Output keeps the original NES CHR + an embedded AI cache section; PpuUltra's per-tile resolver splices the upscales in at render time, preserving NES-shape banking + OAM + pattern-base behaviour.
> - **CHR-RAM games** — upscale tiles in the background as PRG uploads them. Game keeps rendering with nearest-neighbour fallback; tiles upgrade to AI quality as the model replies. Results persist back into the `.poncho` file via the same cache section, so each play session permanently upgrades the cartridge.
>
> The default path is always nearest-neighbour — no model dependency. Users opt in by selecting a model in **Settings → AI upscale**. The architecture supports a separate model choice for ROM bake-now and RAM runtime so users can pick "heavy + slow" for the one-shot bake and "light + fast" for live render.
>
> *Earlier drafts of this plan targeted Google's nanobanana / Gemini 2.5 Flash Image cloud API. That implementation has been removed (v0.4 Phase 4.7) — see CHANGELOG. The infrastructure (cache section, runtime worker, PpuUltra resolver hook, repack/write-back, registry) survives unchanged; only the cloud-API client + Gemini-text prompt-builder were stripped. New models plug in via the registry in `src/convert/upscale-registry.ts`.*

## Why this split

### CHR-ROM is fixed → bake at conversion

The CHR data is fully knowable at conversion time. Pre-baking via the API is a one-shot operation; the user pays the cost once and gets full-quality rendering forever. Output is a native-mode `.poncho` with the entire 32×32 8 bpp CHR embedded. PpuUltra's existing native render path handles it with zero runtime AI involvement.

A 256 KB MMC3 CHR-ROM may have up to ~16 000 tiles. With aggressive deduplication (many tiles are identical or palette-permutations) we typically end up with a few thousand unique calls × 1–2 s each = several minutes. **A progress bar is mandatory** with:

- Tiles processed / total (cache hits separately)
- Estimated time remaining
- Cancel button (preserves what's been cached so far — no progress lost)

### CHR-RAM is dynamic → upscale at runtime

PRG generates CHR-RAM tile data at runtime via `$2007` writes. There is *no way* to know ahead of time which tiles a game will produce without running it. So:

- The runtime keeps using v0.3's nearest-neighbour 4×4 fallback for every tile (always). This guarantees the framebuffer is never stale, never blocked, never empty.
- In parallel, a Web Worker watches `$2007` writes, hashes affected tiles, and queues them to the AI service. When the API replies, the worker writes the 32×32 8 bpp result into a *parallel* native-CHR buffer.
- PpuUltra's per-tile render branch checks the parallel buffer first: if a native version exists for this tile, paint it directly; otherwise fall back to nearest-neighbour. Tiles "pop in" individually as the API replies — typically within a second of being uploaded.

This is "realtime" in the playability sense (the game never stalls) but *not* sub-frame (per-tile latency is still 0.5–3 s on first sight). Tiles seen in prior sessions render at full quality immediately, because the cartridge remembers them — see next.

### Self-upgrading `.poncho` file

When the AI worker completes a tile, the result is written **back into the `.poncho` file's AI cache section**. Triggers: game unload, periodic 60 s flush if dirty, and an explicit "Save AI progress" button. Next time the cartridge loads, the runtime preloads every cached tile from the file before rendering — no API calls needed for tiles seen in prior sessions.

The cartridge therefore becomes monotonically better-quality across plays:

- **First session**: mostly nearest-neighbour, tiles upgrade as encountered, file grows.
- **Second session**: tiles encountered last time are already AI quality; only new tiles need the API.
- **Eventually**: the file caches every tile the game ever produces. AI calls drop to zero. The runtime is purely native-quality with no API dependency.

Why this beats a pure IndexedDB-cache approach:

- **Portable** — moving the `.poncho` to another browser/device or sharing it carries the upgrades.
- **Predictable** — no cache warm-up between sessions; the file *is* the cache.
- **Self-contained** — a friend without an API key plays the version you upgraded.

A future stretch goal: a small **local upscaling model on WebGPU** would make per-tile latency low enough for genuine sub-frame realtime upscaling. Phase 5 stretch.

## Architecture

### PonchoROM AI cache section

A new optional section sits between CHR and the trailer, gated by header `flags.aiCachePresent` (bit 2):

```
[ Header (64) ] [ Palette ] [ PRG ] [ CHR ] [ AI cache (optional) ] [ Trailer (optional) ]
```

Layout of the AI cache section:

```
4 bytes        magic 'AICH' (0x41 0x49 0x43 0x48)
2 bytes        format version (=1)
2 bytes        model identifier (1 = nanobanana-2.5-flash; 0 = unspecified)
4 bytes        entry count N (uint32 LE)
─── entry × N (1056 bytes each) ───
  16 bytes     SHA-256-truncated-128 of (16-byte NES tile bytes ++ 16-byte sub-palette indices)
  16 bytes     raw NES tile bytes (verifiable: if the cache is stale relative to current CHR
               content, a hash mismatch on lookup signals "regenerate")
  1024 bytes   upscaled 32×32 8 bpp Poncho tile
```

On cartridge load, `PonchoCartridge` builds an in-memory `Map<hash, native-tile-offset>` from the cache section. Lookups become O(1). Total size for a CHR-RAM game with ~500 unique tiles seen: ~530 KB — large but tolerable on the order of an MMC3 CHR-ROM.

If the model identifier in the section header doesn't match the user's currently-configured upscaler, the runtime treats every cached entry as a miss (re-upscales). Old entries survive in the file until overwritten — no destructive purge needed.

### Data flow — CHR-ROM bake-now (conversion time)

```
┌──────────────┐     ┌──────────────┐     ┌──────────────────┐     ┌─────────────────┐
│ iNES bytes   │────►│ extract +    │────►│ for each tile:   │────►│ assemble        │
│ (web upload) │     │ dedupe NES   │     │   global cache   │     │ native-mode     │
│              │     │ tiles        │     │   else api.up-   │     │ .poncho         │
│              │     │              │     │   scale          │     │ (upscaledMode=0)│
└──────────────┘     └──────────────┘     └──────────────────┘     └─────────────────┘
                                                  │
                                                  ▼
                                          ┌──────────────┐
                                          │ global tile  │
                                          │ cache (IDB)  │
                                          └──────────────┘
```

Output: native-mode `.poncho` with full 32×32 8 bpp CHR baked in. No AI cache section needed (everything is in CHR proper). PpuUltra's existing native render path handles the rest.

### Data flow — CHR-RAM runtime (during play)

```
                          ┌──────────────────────────────┐
                          │ AI cache section in .poncho  │◄────────┐
                          │  - loaded into mem on cart   │         │
                          │    load                      │         │
                          │  - written back on unload +  │         │
                          │    periodic 60 s flush       │         │
                          └─────────────────┬────────────┘         │
                                            │ get/set              │ AI result
                                            ▼                      │
                          ┌─────────────────────────────┐          │
   PRG executes ──$2007──►│ PonchoMapper.ppuWrite       │          │
                          │  - store NES byte           │          │
                          │  - mark tile dirty          │          │
                          │  - on tile-complete (16 B): │          │
                          │      hash NES tile + sub-   │──────────┤
                          │      palette                │          │
                          │      cache.get(hash)?       │          │
                          │        yes → use native     │          │
                          │        no  → enqueue worker │          │
                          └─────────────────────────────┘          │
                                                                   │
                                                            ┌──────┴──────┐
                                                            │ AI worker   │
                                                            │ (Web Worker:│
                                                            │  debounce + │
                                                            │  dedupe +   │
                                                            │  api call)  │
                                                            └─────────────┘

   PpuUltra render ──► for each tile:
                          mapper.getNativeTile(tileIdx)
                          ├─ cache hit (file or worker)? paint native (full quality)
                          └─ miss?                       paint nearest-neighbour 4×4
```

Key invariants:

- The framebuffer always shows *something* legible. AI never stalls the game.
- Tiles upgrade *atomically* once the API replies — no per-pixel mid-tile transitions.
- The `.poncho` file in the user's library accumulates upscaled tiles across sessions.

### File-write-back

Three triggers cause the cartridge to flush its in-memory AI cache back to the `.poncho` file in the user's library:

1. **Game unload** — closing the cart, switching consoles, leaving the page (`beforeunload`). One write captures the whole session.
2. **Periodic flush** — every 60 s if dirty. Survives crashes.
3. **Manual save** — explicit "Save AI progress" button in Settings (for the paranoid).

Web shell: `WebRomLibrary.add(name, bytes)` overwrites the existing entry. CLI: rewrite the file in place.

The reassembly is straightforward: take the original (header + palette + PRG + CHR), append the AI cache section serialised from in-memory state, append trailer if any. Header `flags.aiCachePresent` flips on if it wasn't already set.

### The nanobanana boundary

Single thin client at `src/convert/nanobanana-client.ts`:

```typescript
interface UpscaleClient {
  upscaleTile(nesBytes: Uint8Array, palette: Uint8Array): Promise<Uint8Array>;
  // nesBytes: 16-byte NES tile (8×8 2 bpp planar)
  // palette: 4 RGBA entries (the sub-palette this tile renders with)
  // returns: 1024-byte Poncho tile (32×32 8 bpp linear)
}
```

Implementation wraps Gemini 2.5 Flash Image:
1. Encode NES tile as a small PNG (8×8 RGBA using the supplied sub-palette)
2. Send to API with prompt: *"Upscale this 8×8 NES sprite tile to 32×32 pixels, preserving the original colour palette and tile boundaries. Output a clean 8 bpp tile."*
3. Receive PNG, decode, map back to palette indices
4. Return 1024 bytes

API key handling: settings panel field, stored in localStorage (browser) or env var (CLI). No key checked into git.

A `MockUpscaleClient` for tests returns deterministic nearest-neighbour output so the rest of the pipeline can be tested without network access.

### Phase 1 — Foundation: format extension + API client + global cache ✅ done

- **PonchoROM format extension**:
  - New header flag `flags.aiCachePresent` (bit 2). Existing `decodeMapperSubmode`/`encodeMapperSubmode` unchanged.
  - New section type `AiCacheSection` between CHR and trailer. Parser/writer additions in `src/core/cart-poncho/`.
  - `parsePonchoRom` returns the new section's offset/length when present.
  - `assemblePonchoRom` accepts an optional `aiCache?: AiCacheSection` parameter.
  - Update `docs/poncho-rom.md` with the format.
- **In-memory tile-cache facade** (`src/convert/tile-cache.ts`): unifies *file-cache* (the cart's AI cache section, in memory) and *global cache* (IndexedDB, shared across all games). Lookup order: file → global → miss. On AI completion, write to BOTH.
- **`UpscaleClient` interface** + `MockUpscaleClient` (deterministic nearest-neighbour) + `NanoBananaClient` (real API). All three live under `src/convert/`.
- **PonchoCartridge integration**: when loading a cart with `aiCachePresent`, build the in-memory `Map<hash, tile>` from the section. Expose it to the runtime so the mapper can use it.
- 30+ unit tests covering: format round-trip, hash dedup, file-cache + global-cache layering, mock client output, model-version invalidation, stale-entry detection (NES tile bytes don't match the cache entry's verifier).

**Effort.** ~4 days (added one day for the format work).

### Phase 2 — CHR-ROM bake-now pipeline (with progress bar) ✅ done

- New high-level converter `convertInesToPonchoAi(bytes, opts)` in `src/convert/ines-to-poncho-ai.ts`. Uses the existing `convertInesToPoncho` for the verbatim shell, then runs AI upscale over the embedded CHR. **CHR-ROM only** — calling this function with a CHR-RAM cart errors out (CHR-RAM goes through the runtime path).
- Per-tile loop: dedupe (many NES tiles are identical or palette-permutations), cache lookup, batched parallel API calls (concurrency cap 4–8).
- Output: native-mode `.poncho` (`upscaledMode = 0`), 64× larger CHR. No AI cache section needed — data is in CHR proper.
- **CLI**: `npm run poncho:convert -- input.nes --ai` triggers AI mode. CHR-ROM games use bake-now; CHR-RAM games skip AI at conversion (since runtime handles it).
- **Web UI**: "Convert .nes" button gains a single "Use AI upscale" toggle. When checked:
  - CHR-ROM games show a modal with progress bar, ETA, cancel — converts to native-mode with full-quality CHR.
  - CHR-RAM games convert instantly (no AI work at conversion); a hint explains "AI upscale will run during play".
- Tests cover: AI client wired correctly, cache populated as expected, partial-failure handling (mark failed tiles, NN fallback for those, succeeded tiles still baked), CHR-RAM games skip the bake step cleanly.

**Effort.** ~5 days.

### Phase 3 — CHR-RAM runtime hooks + self-upgrading file ✅ done

The trickiest phase. Five pieces:

1. **Per-tile native CHR cache in PonchoMapper.** Parallel `Uint8Array(64 × ramSize)` buffer + a `bitmap` of "which tiles have native data". When `ppuWrite` lands in CHR-RAM, mark the affected tile dirty (need to know its hash, which depends on the *full tile* — wait until the PRG has written all 16 bytes before queueing). When the AI worker delivers a result, write to the parallel buffer + flip the bit.
2. **Render-path mode bridging.** PpuUltra's upscaled-CHR render checks the mapper's "native available?" bit per tile. If set, switch that tile's render branch to the native path (32×32 8 bpp direct copy); otherwise the existing 4×4 nearest-neighbour. Per-tile granularity, not per-frame, so the framebuffer becomes increasingly AI-correct as tiles arrive.
3. **AI worker** (Web Worker). Receives dirty-tile messages, debounces (so a fast PRG burst doesn't spam the API), dedupes against the file cache + global cache, calls the API in batches.
4. **File-write-back** in `PonchoNes.unload` + a periodic 60 s flush + explicit "Save AI progress" button. Reassembles `.poncho` bytes and writes back to `WebRomLibrary` (web) or the source file (CLI).
5. **Pre-load file cache on cart load**: `PonchoCartridge` constructor reads the AI cache section into the mapper's in-memory cache before any rendering happens. Subsequent plays start with whatever was upscaled in prior sessions — eventually the file caches every tile the game produces and AI calls drop to zero.

Settings UI:
- Toggle: "AI upscale CHR-RAM during play" (default on if API key configured)
- Toggle: "Save AI progress back to ROM" (default on)
- Live status indicator near the canvas: "AI: 47/128 tiles ready" — fades when complete; reappears when new tiles arrive

**Effort.** ~10 days. Render-path mode bridging + file-write-back-on-unload are both new code paths.

### Phase 4.5 — Stabilisation (alpha → beta) 🚧 in progress

> Most of the original investigation list has either landed or been
> superseded by Phase 4.7's pivot. Reframed for the model-registry
> world: the framework still works, the **only** real model is the NN
> fallback, and visible-quality validation has to wait for Phase 5.

Phases 1-4 land the architecture. The end-to-end output is still **broken** in
practice: an AI-baked `.poncho` renders with scrambled tile contents — colours
swapped, edges shifted, sprite shapes drifting — even after the
`pv3-collapsed-to-pv2` fix in Phase 4. The framework is correct; the
pixel-level fidelity round-trip is not. README is currently flagged "Alpha!"
for this reason.

What we know so far:
- The neutral-palette primer round-trip is now bijective for the 4 chosen
  master indices `[0x0f, 0x16, 0x2a, 0x12]` — pv0..pv3 all map to distinct
  RGBs, so `snapToPaletteIndices` *can* recover them.
- The visible damage is therefore upstream of snap-back: the model's
  output, the PNG decode, or the canvas blit is introducing colour drift
  that pushes pixels into the wrong palette bucket.

Investigation checklist:

1. **Canvas-side smoothing.** `drawImage(bitmap, 0, 0, 32, 32)` may apply
   bilinear filtering. Set `ctx.imageSmoothingEnabled = false` in
   `decodePngTo32` and confirm decoded pixels stay flat. If the model
   returned an exact 32×32 PNG this is a no-op; if it returned a different
   size, this is critical.
2. **Compare the primer to itself.** Mock-test: send a known primer
   through a passthrough "client" that returns the input PNG verbatim,
   verify `snapToPaletteIndices` recovers the *exact* original NES tile.
   If this fails, the bug is in our codec, not the model.
3. **Inspect a real Gemini response.** Add a debug toggle that saves the
   raw response PNG + the snap-back result side-by-side, so we can
   eyeball what the model is doing. Likely findings: anti-aliased edges
   (snap-back picks adjacent palette colour at boundary pixels), softened
   shadows (greys land between two palette greys), unsolicited "creative"
   recolouring.
4. **Prompt fidelity.** Even a perfect codec can't fix it if the model
   re-imagines the tile. Test with stricter prompts: "Output exactly
   these four hex colours: ..." or "Match the input pixel-for-pixel —
   only smooth the edges". Compare A/B outputs.
5. **Sub-palette context loss.** Bake-now sends the neutral palette, not
   the runtime sub-palette. The AI returns shapes that *will* render
   with whatever sub-palette the runtime applies, but if the model
   picks a different *pv assignment* (e.g. swapping foreground/background
   indices) every tile rendering with that sub-palette comes out
   inverted. Mitigation candidates: include a small text token mapping
   "pv0=darkest, pv3=lightest" in the prompt; or reject responses whose
   pv-histogram differs significantly from the input's.
6. **Per-tile vs per-2×2-tile.** Tile-boundary mismatches are a known
   risk (mentioned in Risks above). Worth A/B testing 2×2 grouped
   upscale vs single-tile to see how much of the scrambling is
   inter-tile incoherence rather than per-tile error.
7. **Cache management UI.** Surfaced here because debugging needs it:
   - Settings → Cache → file-cache total per cart, global-cache total,
     "Strip AI cache from this ROM", "Clear global cache".
   - "Strip" is the unblock for the iteration loop — wipe a broken
     bake without re-uploading the source `.nes`.

Acceptance criteria for promoting AI upscale from "Alpha" to "Beta":
- A simple test ROM (e.g. SMB title screen, all-CHR-ROM) AI-baked end-to-end
  is *visibly recognisable as the same image* — same silhouettes, same
  colour assignments, just smoother. Side-by-side with NN-mode it should
  look like an upgrade, not corruption.
- Two consecutive bakes of the same ROM produce identical output (or
  identical modulo the small variance budget we choose to allow).
- A 2-3 minute manual smoke test on three games (one CHR-ROM, one CHR-RAM,
  one MMC3) returns playable cartridges with no obvious palette swaps,
  ghost tiles, or alignment drift.

**Effort.** ~5-7 days. Mostly experimental — heavy iteration, narrow code
changes once a root cause is pinned.

### Phase 4.6 — Extended sub-palettes (richer-than-4-colour AI tiles) ✅ done

PpuUltra used to mask pv to `& 3` in upscaled-mode rendering — capping
each sub-palette at the NES's 4 colours even though the format already
allows 8 bpp tiles (256 pv per tile). This phase lifts the cap for the
**resolver-hit BG render branch** so AI / future-model output can
carry shading and gradient detail; sprite tiles still go through the
NES-tile NN path (transparency semantics for the extended encoding
need a separate design).

**Encoding shipped (backward-compatible with v1 caches; no format-version
bump):**

- `pv 0..3`        sub-palette entries 0..3 verbatim — old AI caches that
                   only used these slots render unchanged.
- `pv 4..87`       84-shade ramp of base 1 (sub-palette entry 1):
                   shade 0 = black, shade 41 = base 1, shade 83 = white.
                   Linear RGB interpolation.
- `pv 88..171`     same shape, ramp of base 2.
- `pv 172..255`    same shape, ramp of base 3.

The earlier sketch proposed `pv = baseIdx * 64 + shade` with a format
bump and a forced re-bake. Final implementation went with the
backward-compatible layout above instead — keeps existing `.poncho`
files renderable, no migration code, no user re-bake. The clean-slate
encoding can come later if 252 shades-per-3-bases ever proves too
narrow.

**Files:**

- New [`src/runtime/extended-palette.ts`](../src/runtime/extended-palette.ts)
  — `buildExtendedSubPalette(subPalette, masterPalette): Uint32Array(256)`
  + `snapToExtendedPalette(r, g, b, ext)` for future RGB-output clients
  (e.g. ESRGAN snap-back in Phase 5).
- [`src/core/ppu-ultra/ppu-ultra.ts`](../src/core/ppu-ultra/ppu-ultra.ts)
  — drops the `pv & 3` mask in the resolver-hit BG branch; lazily
  rebuilds 4 BG extended sub-palettes on the first scanline after a
  palette-RAM or master-palette write (`refreshBgColor()` invalidates).
- New [`tests/runtime/extended-palette.test.ts`](../tests/runtime/extended-palette.test.ts)
  — 10 tests: layout, legacy-pv mirroring, ramp endpoints, base shade,
  monotonic luminance, alpha preservation, error paths, snap-back.

**MockUpscaleClient** stays unchanged: it emits `pv 0..3` from NES
tile bytes (NN expansion), which now hit the legacy slots in the
extended palette → identical output to pre-4.6. Real models that emit
`pv 4..255` will start producing the gradient detail.

**Out of scope here** — moved to a later sub-phase when needed:
- Sprite tiles via the resolver path (transparency design).
- Snap-back inside any `UpscaleClient` (no RGB-output client exists
  yet — Phase 5's ESRGAN client is the first).

### Phase 4.7 — NanoBanana strip + model-registry pivot ✅ done

Removed the Gemini-based `NanoBananaClient` + the per-game prompt-builder
+ the API-key UI. Generalised the seam into a `UpscaleModel` registry
([`src/convert/upscale-registry.ts`](../src/convert/upscale-registry.ts))

(`romModelId`, `ramModelId`) drive bake-now + runtime-worker

`modelConfig[id]` so future models can carry their own settings without
schema migration. Settings UI is now two dropdowns (CHR-ROM and
CHR-RAM) instead of a Gemini API-key field. Only `nearest-neighbour`
ships in this phase — Phase 5 lands the first real model.

### Phase 5 — Local model integration (ESRGAN / ONNX / WebGPU) ⏳ planned (next)

The cleanest target is a small upscale model (ESRGAN-tiny, RealESRGAN-x4-mini,
or similar) running entirely client-side via ONNX Runtime Web on
WebGPU. Comes with several wins over a cloud API:

- **No keys, no quota, no cost.** Model file ships with the build (or
  is fetched once from the dev server / CDN).
- **Sub-frame latency feasible.** A small enough model running on
  WebGPU can do a 32×32 inference in single-digit milliseconds, which
  unlocks true realtime CHR-RAM upscale rather than "tiles pop in".
- **Privacy + offline.** Runs entirely in the user's browser.

Concrete pieces:

1. New `EsrganUpscaleClient` under `src/convert/clients/`. Implements
   `UpscaleClient`. Loads the ONNX file lazily (so the bundle stays
   small until the user picks the model). Per-tile inference: render
   primer with `subPalette` colours → run model → snap output back to
   palette (or to extended palette once Phase 4.6 lands).
2. ONNX model file. Either bundled (~5–20 MB) or fetched on first use
   via `Platform.serverRoms`-style indirection so non-web shells get
   their own loading strategy.
3. Register the model in `upscale-registry.ts` with a stable
   `cacheModelId`.
4. Per-model config: model URL override, quantisation level (fp16 vs
   int8), batch size cap. Stored in `config.ai.modelConfig['esrgan-tiny']`.
5. Model-loading UX in Settings: progress bar on first selection,
   "downloaded" status thereafter, "remove model file" affordance.

**Dependencies.** ONNX Runtime Web (~1–2 MB). WebGPU available in
Chrome / Edge / Safari 16.4+ / Firefox 141+; WASM fallback for the
rest. Target browsers same as the existing core (modern only — see
README).

**Effort.** ~1–2 weeks for a working prototype model + integration;
quality tuning on top.

## Open decisions (model-era)

1. **Model packaging.** Ship the ONNX file in the bundle (~5–20 MB
   added to the build) or fetch on first use? Recommendation: fetch
   on first selection, cache via `serverRoms`-style indirection so
   non-web shells get their own loading strategy. Settings UI shows a
   one-time progress bar then "downloaded" status.
2. **Fallback policy when a model fails for a tile.** Same as before:
   substitute nearest-neighbour + warn. Conversions shouldn't crash on
   a single bad inference.
3. **Cache scope.** File-cache + global-cache (recommended) —
   file-cache is portable with the `.poncho`; global-cache (IndexedDB)
   catches reuse across games. Both keyed by tile-hash.
4. **File-write-back default.** Save AI progress back to ROM by
   default? Recommendation: default ON for CHR-RAM (where new tiles
   show up at runtime) and OFF for CHR-ROM (already baked in the
   conversion).
5. **Cache section limits.** A pathological CHR-RAM game might
   generate thousands of distinct tiles → multi-MB cache section.
   Recommendation: soft cap at 4 K cached tiles per file (~4 MB).
   Beyond that, evict least-recently-used.
6. **Per-workflow vs single model.** Already decided in Phase 4.7:
   the registry exposes both `romModelId` and `ramModelId` so users
   can pair a heavy bake-time model with a light runtime model. UI is
   two dropdowns.

## Risks

- **Model file size + first-load latency.** A 5–20 MB ONNX file pays
  a one-time download cost the first time the user selects the model.
  Mitigation: explicit "downloading…" UI; cache in IndexedDB or via
  `Cache` storage so reloads are free.
- **WebGPU availability.** Chrome / Edge / Safari 16.4+ / Firefox
  141+ have it; older browsers fall back to WASM (slower, may be
  borderline for runtime CHR-RAM). UI flags "WebGPU unavailable —
  bake-now will be slow, runtime will fall back to NN".
- **Output quality variance.** Tile-boundary mismatches still apply
  to local models (a sky tile next to a brick tile, upscaled
  separately, may not seam cleanly). Mitigation: include 1-tile bleed
  context; or upscale in 2 × 2 tile groups; or pick a model trained
  on pixel-art seams.
- **Stale cache entries when models update.** The cache section's
  `model identifier` byte handles this; cached entries from a
  different model render via the seed but don't get rewritten until
  the active model produces fresh output for that tile.
- **Hot-loop performance.** Per-tile branching in PpuUltra's render
  loop adds a few ns per pixel. ~983 k pixels per frame at 60 fps;
  even 1 ns / pixel is ~1 ms / frame — borderline. Profile early.
- **File-write-back races.** Two tabs with the same ROM open could
  clobber each other's AI cache. Mitigation: serialise via IndexedDB
  transactions; additive merge on conflict (never lose tiles).
- **Cache section bloat.** Heavy CHR-RAM games accumulate megabytes
  over many sessions. Soft cap mitigates; manual "Strip AI cache"
  Settings affordance for extreme cases.

## Total estimate

~3–4 weeks calendar time. Phase 3 (runtime hooks) is the highest-risk single phase; budget extra for the render-path mode bridging.
