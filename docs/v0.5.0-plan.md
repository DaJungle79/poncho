# Poncho v0.5.0 — Plan

> **Goal.** Add real-time pixel-art-aware upscaling filters that improve the look of every game across both consoles (Classic NES and Poncho-NES). Headline scaler is **xBRZ** with palette-aware snap-back into the Phase 4.6 extended sub-palette; **MMPX** ships alongside as the fast / faithful alternative. Ramp interpolation gets a perceptual upgrade so xBRZ's anti-aliased edges land on visually-uniform shades.

## Context

v0.4 shipped the AI cache + extended sub-palette infrastructure but stripped all candidate ML models from the UI after each failed the quality bar. v0.5 fills the visual gap with **deterministic** real-time scalers — no model files, no inference, no quality-bar gymnastics. The same algorithms that have been the gold standard for pixel-art emulation since 2003 (HQx) and 2012 (xBRZ); just wired into Poncho's renderer pipeline and, for Poncho-NES, into the per-tile resolver.

Why deterministic scalers belong in v0.5 alongside the v0.4 ML infrastructure (not a replacement):

- **xBRZ on the Phase 4.6 extended palette is novel.** Every other emulator's xBRZ is constrained to the source palette. Poncho's runtime has 84 evenly-spaced shades per sub-palette base ready and waiting; xBRZ's RGB midpoints can snap into them. Result: anti-aliased edges with *real* intermediate colors, not the closest-source-color approximation.
- **MMPX is a 200-LOC port** that ships alongside for users who want clean pixel boundaries instead of curve-fitted "remastered" output.
- **Both work on Classic NES too** (256×240 upscale to 1024×960 / 768×720 / 512×480) — first time in Poncho that Classic mode gets a non-NN scaler.
- Self-upgrading `.poncho` files inherit the benefit: xBRZ output snapped to extended-pv values can be cached in the AI cache section. Same write-back machinery that v0.3/v0.4 built.

## Architecture: where do scalers live?

There are **three** distinct upscaling layers in Poncho, at different points in the pipeline. Knowing which is which avoids the "is xBRZ a scaler or an UpscaleClient?" confusion later.

| | Layer | When it runs | Input → Output | What v0.5 does to it |
|---|---|---|---|---|
| **A** | Renderer-pipeline `Scaler` (`src/renderer/scalers/`) | Runtime, every frame, post-render. | Full framebuffer (256×240 or 1024×960) → canvas size. | **Phase 1 + 2** add `XbrzScaler` and `MmpxScaler` here. |
| **B** | PpuUltra per-tile NN (`renderScanlineUpscaled` resolver-miss branch) | Runtime, per tile, per scanline. | 8×8 NES tile → inline 32×32 framebuffer region, NN-expanded. | **Untouched.** Stays as the cheap fallback when the AI cache has no entry for this tile. Replacing it with xBRZ would make the render hot path 5-15 ms / frame more expensive. |
| **C** | `UpscaleClient` (`src/convert/upscale-client.ts`) — convert-time bake or runtime worker | Convert time (CHR-ROM bake) or background runtime (CHR-RAM). | 8×8 NES tile + 4-byte sub-palette → 1024-byte cached pv tile in `.poncho` AI cache section. | **Phase 3** adds `XbrzUpscaleClient` here. Output snaps RGB midpoints to extended-palette pv values; cacheable + write-back-able to the `.poncho`. |

**Why layers A and C are both useful (and not redundant):**

- **Classic NES** has no layer C — there's no `.poncho`. xBRZ at layer A is the *only* option for Classic NES.
- **Poncho-NES with a layer-C bake** (e.g. converted with `XbrzUpscaleClient`) caches xBRZ-quality 32×32 tiles in the cart. At runtime, PpuUltra's resolver-hit branch reads them and paints via the extended palette. **Layer A xBRZ is NOT re-applied** — the framebuffer is already xBRZ-quality. Re-running xBRZ would cost 5-15 ms / frame for zero benefit, and can introduce halo/ringing artefacts because xBRZ is designed for hard pixel-art edges, not smooth gradients.
- **Poncho-NES with no layer-C bake** falls through to layer B (per-tile NN inside PpuUltra). Layer A xBRZ on top *can* smooth the NN-rendered framebuffer at frame-render time — that's a valid user choice for unbaked carts.
- **Display-size upscaling** (canvas larger than framebuffer): use plain NN, never xBRZ-on-top-of-xBRZ. The framebuffer detail is already there; cheap pixel doubling carries it through cleanly.

**One-line summary of the per-cart user path:**

| Cart | Recommended layer A | Recommended layer C |
|---|---|---|
| Classic NES | xBRZ 2x / 3x / 4x (or NN) | n/a |
| Poncho-NES, plain `convertInesToPoncho` (no bake) | xBRZ 2x / 3x / 4x (or NN) | none |
| Poncho-NES, bake with NN | NN (display-size pass-through) | `MockUpscaleClient` |
| Poncho-NES, bake with xBRZ (the v0.5 headline) | NN (display-size pass-through) | `XbrzUpscaleClient` |

You pay xBRZ's cost **either** at convert-time (layer C — once, persists in the cart) **or** at runtime (layer A — every frame). For Poncho-NES carts the layer-C path is strictly better. For Classic NES layer A is the only option.

## Why xBRZ + MMPX, not the rest

Surveyed in the kickoff conversation:

| Algorithm | Decision |
|---|---|
| **xBRZ** | ✅ ship. Best pixel-art quality. Curve-fits diagonal edges. Synthesises RGB midpoints — exactly what the extended palette needs. |
| **MMPX** | ✅ ship. ~1-3 ms / frame. Outputs source pixels only — preserves "pixel art look". Per-tile cacheable (3×3 kernel doesn't cross 32×32 tile interiors). |
| **HQ2x / HQ3x / HQ4x** | ❌ skip. Predates xBRZ; same shape worse output. Nostalgia preset only. |
| **Scale2x / Scale3x** | ❌ skip. Minimal smoothing — covered by MMPX with cleaner kernel. |
| **2xSaI / Super Eagle** | ❌ skip. Historic. |
| **CleanEdge** | ⏭ defer. GPU-shader-only — needs WebGL pipeline first. |
| **CRT-Royale / Lottes CRT** | ⏭ defer to a future "CRT/post-filter" minor release. |
| **Blargg NTSC** | ❌ skip. LGPL-2.1 doesn't compose cleanly with Poncho's GPL-3.0. |

## Quality bar for v0.5

A scaler ships if **all** of these are true on the manual smoke set (SMB, Bomberman, Castlevania, an MMC3 mid-level, a Poncho-NES upscaled-mode cart):

1. **Visible improvement vs. nearest-neighbour** on the headline screenshot. Non-controversial side-by-side comparison.
2. **No artefacts on still frames.** No haloing, no rainbow seams, no tile-boundary discontinuities on continuous surfaces.
3. **No artefacts on motion.** Sprites don't shimmer, scrolling backgrounds don't crawl, status bars don't ripple.
4. **Frame-time budget respected.** ≤ 8 ms / frame on a mid-tier laptop (target: M1 / Ryzen 5000) at the user's selected output resolution.
5. **Determinism.** Two passes over the same frame produce byte-identical output. Required for `.poncho` write-back.
6. **Per-tile cacheable on Poncho-NES upscaled mode.** Output of running the scaler on tile `T` with sub-palette `S` is the same regardless of `T`'s neighbors. (xBRZ's 5×5 kernel violates this for boundary pixels — see Phase 3 design notes.)

### Phase 1 — xBRZ port + Scaler integration

**Goal.** Drop xBRZ 2× / 3× / 4× / 5× / 6× into `src/renderer/scalers/` so the existing render pipeline can swap it in alongside `NearestNeighborScaler`.

**Reference implementation.** Zenju's xBRZ (C++, MIT). Several JS ports exist; we'll TypeScript-port the canonical C++ rather than depend on a npm package — keeps zero runtime deps and lets us optimise for our specific framebuffer shape.

**Algorithm overview** (so future readers don't have to reverse-engineer from code):

xBRZ is a **pattern-match-and-blend** scaler. For each output pixel, it:

1. Walks a 5×5 neighborhood of source pixels.
2. Detects edge orientation by comparing color distances (YCbCr-weighted L1, then a "different / same" threshold).
3. Picks one of ~24 edge patterns; each pattern has hardcoded blend weights for the output sub-pixels.
4. Outputs alpha-blended RGB.

Key implementation details:
- **Color distance** uses YCbCr weights (Y=48, Cb=7, Cr=6 in the canonical version). Tuned for perceptual edge detection — purely-Euclidean RGB distance over-blends.
- **Equality threshold** decides whether two pixels are "the same color" for pattern matching. Tunable; default 30 in YCbCr distance units.
- **Dominant orientation** at corners disambiguates between "thin diagonal line" and "two adjacent thick lines".
- **Alpha-blend table** is pre-computed; per-pixel cost is two table lookups + a blend. No floating-point per pixel.

**Deliverables.**

1. **`src/renderer/scalers/xbrz/`** — module:
   - `xbrz.ts` — main entry: `xbrzScale(input: Uint32Array, srcW: number, srcH: number, factor: 2|3|4|5|6, out: Uint32Array): void`
   - `xbrz-tables.ts` — generated lookup tables (alpha blend weights, pattern matrices). Pre-computed at module load; ~2 KB.
   - `xbrz-color.ts` — YCbCr distance + threshold helpers.
2. **`XbrzScaler` implementation** of the existing `Scaler` interface (`apply(input, output) → outputSize`). Registered in `src/renderer/scalers/index.ts` under ids `xbrz-2x`, `xbrz-3x`, `xbrz-4x`, `xbrz-5x`, `xbrz-6x`.
3. **Tests** in `tests/renderer/xbrz.test.ts`:
   - Reference output check: a 4×4 hand-built input with known edge produces the canonical xBRZ output (compared against C++ reference dumps).
   - Edge cases: pure white frame, pure black frame, single-pixel solid color (no edges to detect).
   - Determinism: same input → byte-identical output across 100 calls.
   - Boundary: 1×1 input shouldn't crash.
4. **Benchmark** — `npm run test -- xbrz.bench` measures frame-time for 256×240 → 1024×960 (4×). Target ≤ 8 ms.

**Acceptance.**

- `XbrzScaler` registered in the scaler registry.
- Tests pass.
- A user setting `config.video.scaler = 'xbrz-4x'` in localStorage and reloading sees xBRZ output for both Classic NES and Poncho-NES native-mode framebuffers. (Poncho-NES upscaled-mode scaler integration lands in Phase 3.)

**Out of scope for Phase 1.** The Settings UI dropdown (Phase 5). Palette-aware snap-back (Phase 3). Anything Poncho-NES-specific beyond running on the framebuffer.

### Phase 2 — MMPX port + Scaler integration

**Goal.** Ship MMPX 2× as the fast / faithful alternative to xBRZ.

**Reference implementation.** Morgan McGuire / Mara, "MMPX" (2021), MIT. ~200 LOC C++ / GLSL.

**Algorithm overview.**

MMPX is a **3×3 pattern-match copy** scaler. For each pair of output pixels (vertical / horizontal), it:

1. Reads the 3×3 source neighborhood.
2. Matches against a small set of edge patterns (corners, lines, diagonals).
3. **Copies** one of the 9 input pixels to each output sub-pixel — never synthesises new colors.

The result preserves "pixel art aesthetic" (no curve-fitting, no soft anti-aliasing) while smoothing jagged staircases on diagonal lines.

**Why MMPX in addition to xBRZ?**

- Runtime: ~1-3 ms / frame at 4× combined with NN 2× → leaves room for a future CRT post-filter at 60 FPS on weaker hardware.
- Per-tile cacheable: 3×3 kernel for a 32×32 tile means only 1-pixel borders are neighbor-dependent. Inner 30×30 is fully tile-local. Determinism property easier to guarantee for `.poncho` write-back than xBRZ.
- Aesthetic preference: some users actively dislike xBRZ's curve smoothing as deviating from sprite intent.

**Deliverables.**

1. **`src/renderer/scalers/mmpx/`** — module:
   - `mmpx.ts` — `mmpxScale(input, srcW, srcH, out): void`. Fixed 2× factor.
2. **`MmpxScaler`** registered as `mmpx-2x`. For 4× output, users compose `mmpx-2x` with `nearest-2x` via the existing pre/post-filter pipeline (no new infrastructure).
3. **Tests** — same shape as xBRZ tests.

**Acceptance.**

- `MmpxScaler` registered.
- Tests pass.
- 256×240 → 512×480 in ≤ 3 ms / frame.
- A user setting `config.video.scaler = 'mmpx-2x'` sees MMPX output.

**Out of scope.** "MMPX-EP" custom variant emitting extended-pv values on detected patterns (deferred to v0.6+ if there's user demand). The vanilla algorithm doesn't benefit from the extended palette.

### Phase 3 — Palette-aware xBRZ for Poncho-NES upscaled mode

**Goal.** When xBRZ runs on a Poncho-NES upscaled-mode cart, snap each output pixel back to an extended-palette pv value. Output is a 1024-byte tile that PpuUltra can cache, that the runtime worker can write back to the `.poncho` AI cache section, and that survives across sessions.

**Why this is the headline feature of v0.5.** Every other emulator's xBRZ is a post-render filter — it produces RGB pixels, period. For Poncho-NES we can run xBRZ *inside* the per-tile resolver-hit branch, snap the RGB output back to the 256-entry extended sub-palette, and **cache the result in the cartridge**. Each tile xBRZ-renders gets stored on first encounter; subsequent renders pull from cache. Self-upgrading file, just like the Phase 5a ML pipeline was supposed to deliver, but deterministic and free.

**Architectural placement.**

```
PpuUltra render-scanline-upscaled (resolver-hit branch)
      │
      ▼
  16-byte NES tile + 4-byte sub-palette  ──►  upscale-worker.resolveSync()
      │                                              │
      │                                              ▼ (cache miss)
      │                                       worker enqueues tile
      │                                       for "background xBRZ"
      │                                              │
      │                                              ▼
      │                                       xBRZ + snap-back  ────►  1024-byte native tile
      │                                              │                          │
      │                                              ▼                          │
      │                                       cache populated                   │
      ▼                                              │                          │
  paint native tile via extended palette ◄───────────┘ (next frame on)         │
      │                                                                          │
      └──────── on cart eject / 60 s flush ─────────────────────────────►  .poncho AI cache
```

xBRZ is wrapped as an `UpscaleClient` — same interface ESRGAN/SPAN used. The runtime worker accepts it as a drop-in replacement.

**Snap-back details.**

Inside the xBRZ-as-UpscaleClient implementation, after running 4× xBRZ on the 8×8 NES tile primer (= 32×32 RGBA output):

```
For each of 32×32 = 1024 output pixels:
  rgb = xbrz_output[y][x]
  pv  = snapToExtendedPalette(rgb, sub_palette_extended_table)
  native_tile[y * 32 + x] = pv
```

Same `snapToExtendedPalette()` helper introduced in Phase 4.6 — already exists, already tested. The xBRZ-RGB → pv snap uses the *runtime*-built extended palette for the active sub-palette.

**The 5×5-kernel-vs-32×32-tile boundary problem.**

xBRZ reads up to 2 source pixels outside the tile being rendered. For an 8×8 NES tile primer that means xBRZ wants to peek at the neighbor tiles' pixels — but the upscale worker's contract is "one tile in, one tile out, no neighbors". Two ways to handle it:

- **Option A (recommended):** clamp xBRZ's source-pixel reads at the tile boundary (replicate edge pixels). Output along the 1-pixel tile border is a slight over-smooth but the inner 30×30 is identical to "true" cross-tile xBRZ. Determinism is preserved per-tile; cache write-back is meaningful.
- **Option B:** xBRZ runs on the full 1024×960 framebuffer post-render, and the result is a *display-only* filter (not cacheable). Use `XbrzScaler` from Phase 1 directly. No extended-palette benefit; output is RGB direct to canvas.

Phase 3 ships **Option A** for the upscaled-mode integration. Option B is automatically available too (it's just running `XbrzScaler` from Phase 1 in the post-filter slot).

**Deliverables.**

1. **`src/runtime/xbrz-upscale-client.ts`** — `XbrzUpscaleClient implements UpscaleClient`:
   - 8×8 → 128×128 NN-expanded primer in real sub-palette colors (reuse `renderPrimer` from `OnnxUpscaleClient`).
   - 4× xBRZ on the 128×128 RGBA → 512×512 RGBA.
   - Box-filter 512 → 32 (same as `OnnxUpscaleClient` does for the ESRGAN x4plus path).
   - Per-pixel snap to extended palette → 1024-byte tile.
   - Edge-clamped boundary handling (option A).
   - No async deps — sync-resolvable, but we keep it on the worker pump for pacing reasons.
2. **Registry entry** in `src/convert/upscale-registry.ts`:
   - id: `xbrz-4x-snap`
   - label: `xBRZ 4× (palette-aware, deterministic)`
   - cacheModelId: new constant `AI_CACHE_MODEL_XBRZ_4X` (= `3`).
   - Returns `XbrzUpscaleClient`. No platform context needed.
3. **Convert UX** — the L3 Convert .nes panel's existing "Upscale" checkbox + "Attach custom model" pattern stays, with one addition: a **subtle hint line** ("Defaults to xBRZ 4×") under the checkbox. Default model id flips to `xbrz-4x-snap` (was `nearest-neighbour`).
4. **Tests** in `tests/runtime/xbrz-upscale-client.test.ts`:
   - 1024-byte output for any 16-byte tile + 4-byte sub-palette input.
   - All output bytes are valid pv values (0..255).
   - Same input → byte-identical output (determinism).
   - Sub-palette change with same tile bytes → different output (snap-back is sub-palette-aware).
   - Snapshot tests against the smoke-set tiles (a few hand-picked NES tiles whose expected snap-back pv distribution we lock in).

**Acceptance.**

- A CHR-ROM bake with `--model xbrz-4x-snap` (Node CLI) or via the L3 panel default produces a `.poncho` whose AI cache section contains xBRZ-snapped tiles.
- Headless render of the cart shows the cached tiles painted via extended palette — visibly smoother than NN.
- The cart, played in the browser, renders the same way as the headless test (sanity check that the runtime resolver path is wired).
- For CHR-RAM games, the runtime worker uses xBRZ as the default upscaler. New tiles pop in to xBRZ quality during play; the `.poncho` write-back persists them.

**Out of scope.** Sprite-path xBRZ (Phase 4.6 didn't extend sprites; Phase 3 stays BG-only). Cross-base blend ramps in the extended palette (deferred — would be a separate runtime change, see v0.6 plan).

### Phase 4 — Perceptual ramp interpolation

**Goal.** Replace the linear-sRGB interpolation in `buildExtendedSubPalette()` with perceptually-uniform interpolation (CIELAB or oklch). Snapshot tests update once; no format change; xBRZ + future ML models all benefit.

**Why this matters.**

The current ramps are `lerp_sRGB(black, base, t)`. In sRGB-linear space, the luminance step from 0 to 0.5 is much smaller than 0.5 to 1.0 *as perceived by the human eye*. Result: the lower half of every ramp (shades 0..40) renders as nearly-identical dark colors. xBRZ output that snaps into the lower ramp gets squashed to ~3-5 distinguishable shades instead of 41.

CIELAB or oklch interpolation lays out the 84 shades on a perceptually-uniform path. Every shade is equally distinct from its neighbors. xBRZ blends land on the *visually-correct* mid-shade, not a gamma-distorted approximation.

**Implementation.**

1. **`src/runtime/extended-palette.ts`** — replace `lerp(black, base, t)` and `lerp(base, white, t)` with oklch interpolation. (oklch over CIELAB because it's simpler to compute, has comparable perceptual uniformity, and avoids CIELAB's gamut-clipping issues at the saturated ends.)
2. **`oklch.ts`** — small standalone module with `srgbToOklch()` / `oklchToSrgb()`. Standard polynomial; ~50 LOC. Non-allocating per-call (operates on number tuples).
3. **Snapshot regen** — existing extended-palette tests (Phase 4.6) lock specific ramp shade values. Update the snapshots once.

**The compatibility worry.** Existing `.poncho` files with AI cache sections from v0.4 reference pv values 0..255. Their *meaning* is tied to the runtime ramp interpolation. Switching to oklch changes the rendered RGB for every pv 4..255. Visually that's exactly what we want (better-looking gradients) but it's a subtle behavioral break.

We accept the break: there are no users of v0.4 AI caches at scale (the Phase 5a candidates were all dropped). v0.5 documentation calls this out.

**Tests.**

- Existing `tests/runtime/extended-palette.test.ts` updated.
- New test: oklch round-trip (sRGB → oklch → sRGB ≈ identity within float epsilon).
- Visual diff: a handful of ramp-mid shades should be measurably brighter than the linear-sRGB version.

**Acceptance.**

- All extended-palette tests green.
- xBRZ-baked `.poncho` from Phase 3 renders with visibly smoother gradients (side-by-side screenshot in `docs/v0.5.0-plan.md`).

**Out of scope.** Cross-base blend ramps. Per-tile palette analysis. Sprite extended palette.

## Open questions for v0.5

1. **xBRZ 6× — keep it?** The reference C++ supports up to 6×; Poncho's framebuffer is already 1024×960 in upscaled mode, so 6× = 6144×5760. Users with very high-DPI displays could theoretically use it. Cost in port effort: marginal (the algorithm is the same). Decision: ship it.
2. **Does Phase 3's edge-clamp boundary handling produce visible seams between tiles?** Single-pixel border per tile, scaled 4× = 4-pixel band. Theoretically visible on continuous surfaces. Mitigation if needed: option B (post-render xBRZ on the full framebuffer, no cache write-back). Decision deferred to manual smoke.
3. **Should the Convert UX default flip to xBRZ?** Current default after v0.4 is `nearest-neighbour`. If xBRZ-snap-back ships, it's strictly better than NN for most carts. Argue both ways:
   - **For**: better default UX. New users see the upscaler benefit without configuring.
   - **Against**: deterministic determinism — NN is the most predictable reference; some users want it as the floor. Argued in the Phase 4.7 strip.
   - Decision: yes, flip to `xbrz-4x-snap` as the default. NN stays available via the explicit option.

## What's NOT in v0.5

These are interesting but defer to v0.6:

- **Curated per-cart master palette** (option 3 from the planning conversation). At convert time, scan the iNES PRG for actually-used master indices and replace neighbors with interpolated shades. Format-version bump; convert-time analysis pass.
- **Wider sub-palette** (option 4). 8 or 16 master indices per sub-palette instead of 4. Substantial PpuUltra change; format-version bump.
- **Cross-base blend ramps in the extended palette.** xBRZ blends pv=1 (base 1) ↔ pv=2 (base 2) currently snap to one base or the other. Could carve a small "cross-blend" zone (pv 252..255) covering 1↔2, 2↔3, 1↔3, 1↔BG midpoints.
- **Sprite extended palette.** Phase 4.6 only handled BG. Sprite-0 hit + priority semantics make this non-trivial.
- **MMPX-EP custom variant** that emits extended-pv values on detected patterns. Vanilla MMPX in v0.5 is the priority; the custom variant is an "if users ask for it" follow-up.
- **CRT / phosphor / scanline post-filter.** Could be its own minor release once xBRZ + MMPX are stable.
- **WebGL-shader-based scalers** (CleanEdge, GPU-accelerated xBRZ). Requires WebGL pipeline scaffolding first.
